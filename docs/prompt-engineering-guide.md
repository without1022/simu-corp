# 模拟公司 (SimuCorp) — Agent Prompt工程指南

## 1. 概述

本文档定义了模拟公司 (SimuCorp) 中所有Agent的系统提示词（Soul）的编写规范、测试方法和版本管理规则。适用于提示词Agent和HR Manager（当其自动生成或优化Agent Soul时）。

## 2. Soul结构模板

每个Agent的Soul必须包含以下标准章节：

```markdown
## 角色定义
[一句话描述你是谁，你的核心定位]

## 核心职责
[列出3-7项核心职责，每项用一句话描述]

## 工作流程
[描述该角色的标准工作流程，可包含决策树]

## 行为准则
[列出具体的行为规范，确保Agent行为可预测]

## 工具使用说明
[列出可用工具及用途，必要时说明调用时机]

## 输出格式
[定义标准输出模板，确保回复结构一致]

## 语言指令
[定义工作语言和交互语言规则]

## 示例场景
[至少3个Few-shot示例，覆盖典型场景]
```

## 3. 各章节编写规范

### 3.1 角色定义

- **一句话**说清楚身份和定位
- 使用第一人称“你”
- 明确该角色在组织中的位置

**✅ 好的例子**：
> 你是一个AI组织的总裁助理（Executive Assistant）。你的老板是CEO（人类用户），你协助他管理整个AI Agent组织。

**❌ 不好的例子**：
> 你是EA，负责各种事情，包括路由、审批、会议等。（太简略，没有上下文）

### 3.2 核心职责

- 列出3-7项，不超过7项（超过说明角色职责过于宽泛，应拆分）
- 每项一句话，使用**动作动词**开头（接收、分析、创建、跟踪、汇报等）
- 按重要性排序

### 3.3 工作流程

- 描述角色的**标准工作流**
- 若有分支决策，使用决策树或条件语句
- 明确**触发条件**和**结束条件**

**示例**：
```
## 路由决策流程
1. 解析CEO指令，提取能力标签
2. 查询能力目录
3. 匹配判断：
   - 专业部门 → 分派给该部门经理
   - 分公司有硬件 → 委派给分公司EA
   - 都没有 → 分派给GTF Manager
4. 涉及多部门 → 判断是否发起会议
```

### 3.4 行为准则

- 使用“必须”、“应该”、“不要”等明确的规范性语言
- 覆盖以下方面：
  - **边界情况处理**：模糊指令怎么办
  - **权限边界**：什么可以自己决定，什么必须请示
  - **时效要求**：多长时间内回复、什么时候主动汇报
  - **错误处理**：遇到错误怎么办

### 3.5 工具使用说明

- 列出工具名、用途、调用时机
- 标注风险等级（如果工具文档已定义）
- 如果某个工具有特殊参数要求，简要说明

### 3.6 输出格式

- 为**每种常见的输出类型**定义模板
- 使用Markdown标记结构
- 包含占位符（如 `[Agent名]`）

**示例**：
```
### 任务路由回复格式
已委派给 [Agent名]（[Agent ID]）。
预计处理时间：[预估时长]
我会跟踪进度，完成后通知您。
```

### 3.7 语言指令

- 内部推理语言：统一英文（LLM训练数据以英文为主）
- 与CEO交互语言：跟随CEO使用的语言
- 与其他Agent通信语言：英文
- 文档输出语言：跟随项目设置或CEO语言

### 3.8 示例场景（Few-shot）

- **至少3个**示例
- 覆盖：正常场景、边界场景、错误场景
- 每个示例包含：用户输入 → Agent推理过程 → Agent输出
- 使用 `### 示例N：场景描述` 分隔

## 4. Soul质量评估标准

| 维度 | 权重 | 评估标准 |
|------|------|---------|
| **完整性** | 0.25 | 是否包含所有8个标准章节 |
| **清晰性** | 0.25 | 指令是否明确无歧义，行为准则是否具体可执行 |
| **一致性** | 0.2 | 各章节之间是否有矛盾（如职责说可以自己决定，行为准则说必须请示） |
| **覆盖度** | 0.2 | Few-shot是否覆盖正常、边界、异常场景 |
| **简洁性** | 0.1 | 是否存在冗余描述，是否超过必要长度 |

**评分规则**：
- ≥8.5：优秀，可直接使用
- 7.0-8.4：良好，微调后使用
- 5.0-6.9：需修改，存在明显缺陷
- <5.0：需重写

## 5. Soul测试方法

### 5.1 沙盒回放测试

新Soul或优化后的Soul在正式上线前，必须通过沙盒回放测试：

1. 选取该Agent近10个历史任务
2. 在沙盒中重放每个任务（使用新Soul）
3. 对比新旧Soul的输出：
   - 任务成功率（是否完成）
   - 输出质量（人工或LLM评估1-5分）
   - 执行效率（完成时间）
4. 生成测试报告

**通过标准**：
- 成功率不低于旧Soul
- 质量均分不低于旧Soul
- 效率不低于旧Soul的90%

### 5.2 A/B测试（可选，正式Agent）

1. 将新Soul部署到20%的流量
2. 监控3天（或至少30个任务）
3. 对比指标：成功率、质量评分、效率
4. 若新Soul显著优于旧Soul → 全量发布
5. 若新Soul显著差于旧Soul → 自动回滚，通知HR
6. 若差异不显著 → 延长测试或人工决策

### 5.3 CEO手动测试（新角色）

对于全新的Agent角色（没有历史任务可回放），由CEO或HR手动执行3-5个测试任务，人工评估。

## 6. Soul版本管理

### 6.1 版本号规范

使用语义化版本号：`主版本.次版本.修订版本`

- **主版本**：Soul结构或核心职责发生重大变更（如新增一个核心职责）
- **次版本**：行为准则、输出格式等微调
- **修订版本**：修正拼写错误、完善示例等

### 6.2 变更日志格式

每次Soul更新必须记录：

```markdown
## [1.2.0] — 2026-06-20

### 新增
- 添加了“审批升级判断标准”章节

### 修改
- 调整了路由决策优先级：专业部门 > 分公司 > GTF

### 删除
- 移除了冗余的“每日汇报”要求

### 测试结果
- 沙盒回放测试：10/10通过，质量均分4.2→4.3
- A/B测试：3天，成功率持平，效率提升12%

### 回滚计划
- 若异常，回滚到 v1.1.0
```

### 6.3 回滚机制

- 旧版本Soul永久保留在Git历史中
- HR Manager可通过 `agents.update` 一键回滚到任意历史版本
- 回滚操作记录到审计日志
- 若连续3次更新后绩效下降，自动暂停该Agent的Soul优化，通知HR人工审查

## 8. HR Manager自动生成Soul的检查点

HR Manager在自动生成或优化Soul时，必须检查以下清单：

| 检查项 | 通过标准 |
|--------|---------|
| 角色定位清晰 | 一句话能说清楚这个Agent是干什么的 |
| 职责不超7项 | 核心职责3-7项，超过则需拆分角色 |
| 行为准则可执行 | 每一条准则都有具体的“做什么/不做什么” |
| Few-shot覆盖 | 至少包含正常、边界、错误三种场景 |
| 与工具集一致 | Soul中提到的工具都在Agent的tools配置中 |
| 与基座匹配 | 代码型Agent的Soul不应要求“可视化设计” |
| 语言指令完整 | 包含内部推理语言、交互语言、文档语言规则 |
| 无内部矛盾 | 各章节之间没有互相冲突的指令 |
